## Phase 10 — Production 🔶 IN PROGRESS (code-level hardening done; live deployment is a manual, user-driven step)

### Done this session — security audit + error handling (backend)

- **Fixed a real information-disclosure bug**: nearly every service (`debts`, `payments`, `users`, `telegram`, `notifications`, `stats`, `admin`, `reminders`, `push` — ~35 call sites) threw `InternalServerErrorException(error.message)`, which put the *raw* Supabase/Postgres error text straight into the HTTP response body — a direct violation of CLAUDE.md §41 ("Never show raw technical errors") and a minor info-disclosure risk (could leak table/column names to any caller). Rather than touching all ~35 call sites, added one central `backend/src/common/filters/all-exceptions.filter.ts` (`@Catch()`, wired via `app.useGlobalFilters()` in `main.ts`): it rewrites the message of any `InternalServerErrorException` specifically to a generic Uzbek string, logs the real error server-side via `Logger`, and leaves every other deliberately-authored `HttpException` (400/401/403/404/503/501, all already using safe Uzbek text) untouched. **Verified live**, not just statically: booted the compiled server with dummy env vars and confirmed via `curl` that a forced Supabase failure returns `{"statusCode":500,"message":"Serverda xatolik yuz berdi..."}"` to the client while the real `TypeError: fetch failed` shows up only in the server log.
- **Rate limiting was silently a no-op**: `ThrottlerModule.forRoot(...)` was imported in `app.module.ts` but `ThrottlerGuard` was never registered — so CLAUDE.md §32's "rate limiting where appropriate" wasn't actually enforced anywhere. Added `{ provide: APP_GUARD, useClass: ThrottlerGuard }`. Verified live via `curl` response headers (`X-RateLimit-Limit/Remaining/Reset` now present on every response).
- **CORS was fully open** (`app.enableCors()` with no options reflects any origin). Restricted to a configurable allow-list via new `CORS_ORIGINS` env var (comma-separated), defaulting to open only when unset (local dev convenience). Kept working for the one browser→backend call that actually needs cross-origin access: the public `/confirm/[token]` page's `confirm-actions.tsx` is a client component that calls the API directly from the browser (everything else goes through Next.js Server Actions, which aren't subject to CORS at all). Verified live: requests from an unlisted origin get no `Access-Control-Allow-Origin` header; the configured origin does.
- **Added `helmet`** (new dependency) via `app.use(helmet())` for standard security headers (CSP, HSTS, X-Frame-Options, etc.) — verified present in live response headers.
- **Health-check route was accidentally behind auth**: `GET /` (`AppController.getHello`) had no `@Public()`, so the global `JwtAuthGuard` returned 401 on it — found via live smoke-testing, not by reading the code. Render (or any PaaS) needs an unauthenticated 200 to confirm the service is up, so this would have broken deployment health checks. Fixed with `@Public()`; verified `GET /` now returns 200 live.
- **Uzbekified the last English user-facing strings**: `auth.controller.ts`'s three `NotImplementedException` messages (phone/OTP register/login/OTP stubs) were in English; translated to Uzbek per CLAUDE.md's Uzbek-only text rule.
- **Migration `0006_enable_rls.sql`**: enables row-level security (no policies = deny-all) on every table, as defense-in-depth. Changes nothing functionally today — the backend always connects with `SUPABASE_SERVICE_ROLE_KEY`, which bypasses RLS regardless of whether it's enabled — but closes the door on an *accidental future* mistake (e.g. if an anon key were ever exposed to the frontend, which it currently never is).
- **`render.yaml`** (repo root): a Render Blueprint for the backend service (`rootDir: backend`, build/start commands, health check path `/`, every required env var listed with `sync: false` so Render prompts for the real secret values in its dashboard rather than storing them in the repo; `JWT_SECRET` uses `generateValue: true` so Render mints a strong random one automatically).
- Backend `npm run build`, `npm run lint`, and `npm test` all clean. Confirmed by running `node dist/main.js` (compiled build, not `nest start --watch`) against dummy env vars — the closest thing to a live smoke test possible without a real Supabase project.

### Critical production bug found and fixed (same session, after the above): `record_payment` overload ambiguity broke every payment

After deploying and applying migrations, the user reported "server error" when trying to add a payment. Root cause, confirmed live via `supabase db query --linked` (the CLI's `db query` subcommand runs arbitrary read/write SQL directly against the linked remote project — useful for this kind of live diagnosis, not previously used in this project):

- Migration `0009`'s `create or replace function record_payment(p_debt_id uuid, p_user_id uuid, p_amount numeric, p_note text default null, p_method text default 'cash', p_provider_transaction_id text default null, p_payment_transaction_id uuid default null)` did **not** replace the original 4-parameter function from migration `0002`. Postgres identifies function overloads by their *full declared parameter type list* — appending 3 new trailing parameters (even with defaults) makes it a *different* signature, so `CREATE OR REPLACE` created a **second overload** alongside the original, which was never dropped.
- Every real call site (`PaymentsService.create()`, the manual/cash payment flow — and this affected provider payments identically) calls `.rpc('record_payment', {p_debt_id, p_user_id, p_amount, p_note})` with exactly 4 named parameters. With two overloads present, that call matched **both** (the 7-parameter one via its own defaults for the other 3), so PostgREST/Postgres couldn't resolve which one to call and raised `function record_payment(...) is not unique` — masked by the global exception filter into the generic "Serverda xatolik yuz berdi" every user saw. **This broke 100% of payments (cash and provider) in production** from the moment `0009` was pushed until this fix.
- Confirmed the exact duplicate via `select proname, pg_get_function_identity_arguments(oid) from pg_proc where proname = 'record_payment'` — two rows came back (4-arg and 7-arg) before the fix, one row (7-arg only) after.
- **Fix**: new migration `supabase/migrations/0011_fix_record_payment_overload.sql` — `drop function if exists record_payment(uuid, uuid, numeric, text);`, leaving only the 7-parameter version, which every existing call site already matches correctly (defaults fill the 3 new trailing params). Applied to production via `supabase db push`.
- **Verified live, twice**: (1) `supabase db query --linked` calling `record_payment(...)` with the original 4 named args against a nonexistent debt id now returns a clean `DEBT_NOT_FOUND` (P0001) instead of the "not unique" ambiguity error; (2) booted the compiled backend locally against production and confirmed `POST /debts/:id/payments` (no auth) still correctly returns `401` — i.e. the request pipeline up to the RPC call is intact, and the RPC itself no longer errors on ambiguity.
- **Lesson for any future Postgres function signature change**: `CREATE OR REPLACE FUNCTION` only replaces a function whose declared parameter type list is identical — adding, removing, or reordering parameters (even ones with defaults) silently creates a new overload instead of replacing the old one, unless the old one is explicitly `DROP FUNCTION`ed first (or in the same migration). Always check `pg_proc` for the function name after this kind of change, especially in migrations that widen an existing RPC's signature (as `payments`/`reminders`/similar patterns in this project may do again in the future).
- Committed and pushed as its own migration file (no backend/frontend code changes needed — the bug was purely in the SQL migration, and the application code was already correct).

### 2. Click — reviewed, one real signature bug found and fixed ✅

Click's flow is two-phase (`action=0` Prepare, `action=1` Complete), distinguished by different MD5 `sign_string` formulas. The **original implementation used the same formula for both phases**, but Complete's formula inserts `merchant_prepare_id` into the string (verified via a live web search against Click's public docs and cross-referenced against the well-established community implementation pattern) — Prepare's doesn't have that field yet. Using Prepare's formula for Complete meant **every real Complete webhook would have failed signature verification** the first time real credentials were ever configured, silently breaking 100% of Click payments before they could ever succeed. There was a second, more fundamental bug: Click's Prepare webhook is only an acknowledgment ("can you accept this payment?"), but the original code treated *any* webhook where `action !== 1` as a **payment failure** — meaning Click's Prepare would always be rejected and Click would never even send the follow-up Complete call. Both fixed in `backend/src/payment-providers/providers/click.provider.ts`:
- `doVerifySignature` now branches by `action`, including `merchant_prepare_id` in the hash only for Complete.
- `doParseWebhook` maps Prepare → the new generic `phase: 'create'` (acknowledge only, never moves money) and Complete → `phase: 'complete'` (the money-moving step) — see the interface change below.
- `doBuildSuccessResponse` now returns `merchant_prepare_id` (reusing our own transaction id — Click just echoes back whatever we return here on the follow-up Complete call, so no extra stored state is needed).

### 3. Payme — reviewed, protocol was fundamentally incomplete; rewritten and fixed ✅

The original implementation only ever handled `PerformTransaction`, treating every other JSON-RPC method (`CheckPerformTransaction`, `CreateTransaction`, `CancelTransaction`) as a payment failure — exactly the same class of bug as Click's Prepare issue, but worse: **Payme always calls `CheckPerformTransaction` first**, so the original code would have rejected every real Payme payment attempt at the very first step, before `PerformTransaction` could ever be reached. Verified Payme's real method/param/response shapes via `developer.help.paycom.uz` (live doc fetches during this session, not assumed from memory) before rewriting `backend/src/payment-providers/providers/payme.provider.ts`:
- Implemented `CheckPerformTransaction` (read-only `{result:{allow:true}}` check), `CreateTransaction` (acknowledges Payme's own transaction id against our pending row, doesn't move money), `PerformTransaction` (unchanged — the actual money-moving step), and `CancelTransaction` (marks our row cancelled; explicitly **rejects** cancelling an already-completed transaction rather than silently "succeeding" at a refund that isn't implemented).
- Fixed a second real bug: the JSON-RPC 2.0 envelope's `id` field (which Payme's spec-compliant client requires echoed back verbatim in every response) was previously either missing entirely or, in the error path, had our own internal error *code string* stuffed into it by mistake (`id: code` — never valid for any interpretation of JSON-RPC). Now correctly echoed from the incoming request via a new `ParsedWebhookEvent.rpcId` field.
- Fixed a third bug: `CreateTransaction`'s response's `transaction` field was returning Payme's own transaction id; per Payme's own documented `CheckTransaction` example, this field must be **our** merchant-side reference. Fixed.
- Fixed a fourth bug (`PaymentTransactionsService`, not Payme-specific): `PerformTransaction`'s params only ever carry Payme's own `id` (no amount, no account) — the shared terminal-phase amount-mismatch check unconditionally compared `event.amount` (0, since Perform sends no amount) against the stored amount, which would have rejected **every real `PerformTransaction`** with a false `AMOUNT_MISMATCH`. Found live during testing below, fixed by skipping that check when the webhook call carried no amount at all (the amount was already verified earlier, during Check/Create).
- Perform/Cancel/CheckTransaction calls only carry Payme's own transaction id, never ours — `PaymentTransactionsService.handleWebhook` now falls back to looking our row up by `provider_transaction_id` when the gateway's payload doesn't include our own id, then backfills `event.transactionId` from the found row so every response built afterward is correct regardless of which fields that particular call happened to carry.
- Deliberately **not implemented**: `CheckTransaction` and `GetStatement` — both are read-only reporting/reconciliation methods Payme may call independently of the money-moving flow; not required for a payment to complete, left as a documented gap rather than guessed at with no sandbox to verify against.

**A fifth, more serious bug was found only through live simulation (see Testing below), not code review**: the terminal "apply payment" branch's only idempotency guard was `if (transaction.status === 'success') return success` — it had **no check for `'cancelled'` or `'failed'`**. A `CancelTransaction` followed by a late/duplicated `PerformTransaction` call for the same transaction fell straight through the missing guard and **applied the payment anyway**, despite the transaction already being cancelled. Fixed in `PaymentTransactionsService.handleWebhook`: any transaction not in `'pending'` or `'success'` state now rejects the terminal call outright, and this exact attack sequence (cancel → late perform) was re-run after the fix to confirm no payment leaks through.

Frontend `payment-method-picker.tsx`'s provider list and backend `payment-providers.service.ts`'s registry both use the identical `yagona_pay` identifier — confirmed no mismatch. `isConfigured()` still correctly gates every method behind `PROVIDER_NOT_CONFIGURED` until real `YAGONA_PAY_*` env vars are set (verified live, see Testing below).

### 5. Receipt PDF — root cause found and fixed ✅ (the user's top-priority item)

**Root cause**: `receipts.controller.ts`/`public-receipts.controller.ts`'s `downloadPdf` handlers returned a raw `Buffer` from the controller method. NestJS's Express adapter (`RouterResponseController` → `ExpressAdapter.reply()`) calls `response.json(body)` for **any** object return value that isn't a `StreamableFile` — and a `Buffer` *is* a JS object. So every "PDF download," in every environment, in every session since Phase 11 Stage 3 first built this feature, actually served `{"type":"Buffer","data":[37,80,68,70,...]}` (the JSON-serialized byte array) with a `Content-Type: application/pdf` header lying about what the body actually was — never real PDF bytes. This is why the earlier session's `WebApp.openLink()` fix (commit `045838b`) didn't actually fix anything: it corrected *how* the Mini App navigates to the URL, but the URL itself never returned a valid file, in Telegram or a normal browser. **Confirmed via direct reproduction**: `Buffer.from(await PDFDocument.save())` piped through `JSON.stringify` starts with `{"type":"Buffer"` instead of `%PDF-`.
- **Fix**: both `downloadPdf` handlers now return `new StreamableFile(pdf, { type: 'application/pdf', disposition: 'attachment; filename="<receipt_number>.pdf"' })` — Nest's documented mechanism for exactly this case, which takes the `reply()` branch that pipes bytes through untouched instead of JSON-encoding them. Also fixes a second, smaller gap: `Content-Disposition` was never set before, so downloads had no real filename.
- **Verified live against a real receipt already in production** (`QD-20260817-000001`, created in an earlier session): booted the compiled backend against real Supabase, curled the public receipt PDF route, and confirmed via `file` that the downloaded bytes are a genuine "PDF document, version 1.7" — headers show `Content-Type: application/pdf`, `Content-Disposition: attachment; filename="QD-20260817-000001.pdf"`, and the correct `Content-Length`.
